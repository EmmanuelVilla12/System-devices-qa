# 1.3 Tipos de prueba y técnicas de diseño · HU-001

**Fase:** Preparación
[Volver al flujo](../00_Flujo_metodologico.md)

## Dos preguntas distintas

| Pregunta | Clasificación | Aplicación en HU-001 |
|---|---|---|
| ¿Qué aspecto se evalúa? | **Funcional** o **no funcional** | Funcional: crear la cuenta, validar datos, mostrar condiciones, rechazar solicitudes inválidas. No funcional (solo los de la ficha): protección de la contraseña (RNF-001), accesibilidad (RNF-004), adaptación (RNF-005) y límite de uso (RNF-006). |
| ¿Cómo se diseñan los casos? | **Caja negra** o **caja blanca** | Caja negra: los casos se derivan de la ficha y sus criterios, sin ver el código. Caja blanca: no se aplica en este banco; corresponde a pruebas unitarias del equipo de desarrollo. |

## Niveles de prueba

| Nivel | ¿Se aplica? | Justificación |
|---|---|---|
| Unitario | No en este banco | Lo realiza desarrollo sobre las funciones de validación (caja blanca). |
| Integración | Sí (ACC-REG-017) | La regla de la ficha dice que la cuenta aceptada se usa para iniciar sesión con HU-002. |
| Sistema | Sí | Todos los casos recorren la aplicación como la persona usuaria. |
| Aceptación | Sí | Cada caso se traza a un criterio aceptado por el Product Owner. |

## Tipo de prueba y técnica por criterio

| Criterio / condición | Tipo de prueba | Técnica | Justificación |
|---|---|---|---|
| CA-HU-001-01 | Funcional | Partición de equivalencia + valores límite | Hay tres clases válidas de rol y dos rangos con límites explícitos (nombre 3–50, contraseña 8–72): cada rol y cada límite aceptado es una condición distinta. |
| CA-HU-001-02 | Funcional | Partición de equivalencia | «Correo registrado» es una clase inválida única; basta un representante. |
| CA-HU-001-03 | Funcional | Partición de equivalencia + valores límite | La ficha da límites numéricos del nombre (2 y 51 los bordes inválidos) y clases de dato vacío o formato inválido; cada dato incumple una sola condición. |
| CA-HU-001-04 | Funcional | Transición de estados | El criterio habla de una lista que cambia «mientras escribo o corrijo»: lo que importa es el paso de cumplida a no cumplida y viceversa. |
| CA-HU-001-05 | Funcional | Partición de equivalencia + valores límite | Seis condiciones independientes; un dato por condición (7 y 73 para longitud) permite saber qué validación falta. |
| CA-HU-001-06 | Funcional | Partición de equivalencia | Dominio cerrado de tres valores; se verifican las opciones y los dos roles no cubiertos por el básico. |
| CA-HU-001-07 · RNF-006 | No funcional con efecto funcional | Valores límite + transición de estados | El límite «3 por minuto» se prueba en la 3.ª (aceptada) y 4.ª (rechazada) dentro de la ventana, y el regreso al estado disponible. |
| RNF-001 | No funcional (seguridad) | Inspección de respuesta y almacenamiento | La condición no es visible en pantalla: requiere buscar el valor en la respuesta y en el almacenamiento. |
| RNF-004 | No funcional (accesibilidad) | Recorrido con teclado y con lector | La ficha pide teclado, campos identificados y errores accesibles: se verifican con las herramientas que usa la persona. |
| RNF-005 | No funcional (adaptación) | Recorrido en dos tamaños de pantalla | La ficha nombra computador y teléfono; se elige un tamaño representativo de cada uno. |

## Técnicas seleccionadas

### Partición de equivalencia

| Campo | Clases válidas | Clases inválidas |
|---|---|---|
| Nombre | 3–50 caracteres | vacío · < 3 · > 50 |
| Correo | formato válido no registrado | vacío · registrado · sin @ · con dos @ · sin parte local |
| Contraseña | cumple todas las condiciones | vacía · < 8 · > 72 · sin mayúscula · sin minúscula · sin número · con espacio · con el nombre |
| Rol | usuario · soporte · administrador | sin seleccionar |

Cada dato inválido incumple **una sola** condición; así, si el sistema lo acepta, se sabe qué validación falta.

### Análisis de valores límite

| Regla | Justo por debajo | En el límite | Justo por encima |
|---|---|---|---|
| Nombre ≥ 3 | 2 → rechazo (ACC-REG-009) | 3 → acepta (ACC-REG-005) | — |
| Nombre ≤ 50 | — | 50 → acepta (ACC-REG-005) | 51 → rechazo (ACC-REG-009) |
| Contraseña ≥ 8 | 7 → rechazo (ACC-REG-012) | 8 → acepta (ACC-REG-006) | — |
| Contraseña ≤ 72 | — | 72 → acepta (ACC-REG-006) | 73 → rechazo (ACC-REG-012) |
| Solicitudes ≤ 3 por minuto | — | 3.ª → acepta | 4.ª → rechazo (ACC-REG-016) |

### Transición de estados de la lista de condiciones (ACC-REG-011)

Nombre de la persona: `Tomás Quiroga`.

| Valor escrito | Longitud 8–72 | Mayúscula | Minúscula | Número | Sin espacios | Sin el nombre |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| `7` | ✗ | ✗ | ✗ | ✓ | ✓ | ✓ |
| `7k` | ✗ | ✗ | ✓ | ✓ | ✓ | ✓ |
| `7kR` | ✗ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `7kRwpzqx` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `7kRw␠pzqx` | ✓ | ✓ | ✓ | ✓ | ✗ | ✓ |
| `7kRwpzqx` (espacio borrado) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `7kRwpzqxQuiroga` | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |

Ventana de frecuencia (ACC-REG-016): *disponible (0–2 solicitudes)* → *en el límite (3)* → *rechazo (4.ª)* → *disponible otra vez tras la espera*.

### Recorridos no funcionales

Teclado y lector de pantalla (RNF-004), dos tamaños de pantalla (RNF-005) e inspección de respuesta y almacenamiento (RNF-001). No se usan RNF que la ficha de HU-001 no lista.

## Fuera de alcance

Rendimiento y carga (la ficha no define tiempos), caja blanca del validador, automatización y condiciones de calidad que la ficha de HU-001 no lista. Se registran como posibles mejoras en [4.3](../04_Evaluacion/4.3_Plan_de_mejora_continua.md).
