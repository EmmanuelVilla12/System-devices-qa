# 1.3 Tipos de prueba y técnicas de diseño · HU-006

**Fase:** Preparación
[Volver al flujo](../00_Flujo_metodologico.md)

## Dos preguntas distintas

| Pregunta | Clasificación | Aplicación en HU-006 |
|---|---|---|
| ¿Qué aspecto se evalúa? | **Funcional** o **no funcional** | Funcional: cerrar sesión por caducidad, cerrión por invalidación, acceso denegado por rol. No funcional (solo los de la ficha): comprobar sesión y rol (RNF-002), comunicar necesidad de nuevo ingreso (RNF-004, RNF-005). |
| ¿Cómo se diseñan los casos? | **Caja negra** o **caja blanca** | Caja negra: los casos se derivan de la ficha y sus criterios, sin ver el código. Caja blanca: no se aplica en este banco; corresponde a pruebas unitarias del equipo de desarrollo. |

## Niveles de prueba

| Nivel | ¿Se aplica? | Justificación |
|---|---|---|
| Unitario | No en este banco | Lo realiza desarrollo sobre las funciones de validación de sesión (caja blanca). |
| Integración | Sí (ACC-INV-004) | La regla de la ficha dice que el rol insuficiente no cierra la sesión; se verifica la integración con el módulo de autorización. |
| Sistema | Sí | Todos los casos recorren la aplicación como la persona usuaria, sin sesión o con sesión inválida. |
| Aceptación | Sí | Cada caso se traza a un criterio aceptado por el Product Owner. |

## Tipo de prueba y técnica por criterio

| Criterio / condición | Tipo de prueba | Técnica | Justificación |
|---|---|---|---|
| CA-HU-006-01 | Funcional | Partición de equivalencia | Dos clases de sesión: caducada y no caducada; cada una es una condición distinta. |
| CA-HU-006-02 | Funcional | Partición de equivalencia | Dos clases de sesión: rechazada como inválida y no rechazada; cada una es una condición distinta. |
| CA-HU-006-03 | Funcional | Partición de equivalencia | Acceso a pantalla protegida después de cierre vs acceso bloqueado; cada condición es un escenario. |
| CA-HU-006-04 | Funcional | Partición de equivalencia | Rol con permiso vs rol sin permiso; dos clases distintas que dan resultados diferentes. |
| RNF-002 | No funcional con efecto funcional | Inspección de respuesta y conservación de datos | La condición no es visible en pantalla: requiere buscar el valor en la respuesta y verificar que los datos no se modificaron. |
| RNF-004 | No funcional (accesibilidad) | Recorrido con teclado y lector | La ficha pide que el mensaje sea legible con lector de pantalla y por teclado. |
| RNF-005 | No funcional (adaptación) | Recorrido en dos tamaños de pantalla | La ficha nombra computador y teléfono; se eligen tamaños representativos de cada uno. |

## Técnicas seleccionadas

### Partición de equivalencia

| Elemento | Clase Válida | Clase Inválida |
|---|---|---|
| Estado sesión | Caducada (TTL expirado) | No caducada (TTL vigente) |
| Origen del rechazo | Servicio declara inválida | Aplicación la tiene como válida |
| Rol tiene permiso | No tiene permiso | Tiene permiso para la función |
| Recuperación pantalla | No se recupera acceso | Se recupera acceso |

Cada dato inválido incumple **una sola** condición; así, si el sistema lo acepta, se sabe qué validación falta.

### Inspección de respuesta y almacenamiento (RNF-002)

| Elemento | Verificar | Cómo |
|---|---|---|
| Sesión en respuesta | Ausente o con marca de caducidad | Buscar en headers o cuerpo de la respuesta HTTP |
| Datos conservados | Registros no modificados | Comparar estado antes y después del rechazo |
| Marca de invalidación | Presente en sesión | Revisar campo `invalidated_at` o similar |

### Recorridos no funcionales (RNF-004 y RNF-005)

- Teclado y lector de pantalla (RNF-004): el mensaje "Inicie sesión nuevamente" debe ser alcanzable y legible.
- Dos tamaños de pantalla (RNF-005): computador (1366×768) y teléfono (390×844). No se usan RNF que la ficha de HU-006 no lista.
